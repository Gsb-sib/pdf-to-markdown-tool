# 文字与公式验证记录

验证日期：2026-11-10。平台为 Windows x64、Java 17、CPU 推理。本记录区分软件行为、文字字符一致性和公式数学结构，不能将其中一种分数用作另一种准确率。

## 结论与发布状态

公式识别已有明显改进：原先不可靠的复杂分式、积分上下限和上下标改用独立数学模型，检测到的公式保留裁剪原图。固定合成样本的 28 个公式实例人工核对通过。但真实教材仍有漏检、未转换上下标，以及检测框混入正文的问题，**没有证据证明复杂教材公式达到 99%**。2026-11-11 发布版将公式增强标为实验功能，公开工具源码并保留这些限制；发布不代表公式准确率验证全部通过。

28 个实例来自 14 个不同公式各自的文字 PDF 和扫描 PDF 表示，不是 28 个独立公式。样本少、字体和页面种类有限，不能据此推断任意文档达到 99%。

## 文字回归

固定 21 份文字/扫描 PDF，预先给定参考文字共 7,702 个字符。使用 Levenshtein 编辑距离按参考字符数加权：`100 × (1 - 总编辑次数 / 总参考字符数)`。

| 指标 | 结果 |
| --- | --- |
| 忽略空白的加权字符一致率 | 99.740327%（20 次编辑 / 7,702 字符） |
| 保留词间空白的一致率 | 98.771211% |
| 单份忽略空白得分至少 99% | 19 / 21 |
| 结构检查 | 通过 |

低清两份分别约 96.70% 和 98.80%，因此“平均超过 99%”不等于“每份 PDF 超过 99%”。本地重复真实 HTTP 回归使用下载脚本取得的 OCR 模型，结果与以上数值一致。此分数不是版式一致率、图片完整率或公式语义正确率。文字评估文件独立保存在本地交付中；仓库不包含用户 PDF。

## 公式模型与固定样本

使用 PaddlePaddle 3.2.2、PaddleOCR 3.6.0、PaddleX 3.6.1；检测器 `PP-DocLayout_plus-L`，默认数学模型 `PP-FormulaNet_plus-L`，CPU 4 线程，页面按 200 DPI 渲染。每份 PDF 初始化一次模型，文档内部复用。

标准答案在识别前固定。人工对照原图检查变量大小写、上下标、分子分母、积分/求和上下限、运算符与结构，不要求 LaTeX 字节完全相同；不能以下载成功、字符相似率或模型自身置信度代替此核对。

| 样本 | 覆盖范围 | 人工结构核对 |
| --- | --- | --- |
| 初始集，文字 PDF | 6 式：质能、勾股、高斯密度、定积分、求和、求根 | 6 / 6 |
| 初始集，扫描 PDF | 同 6 式 | 6 / 6 |
| 保留集，文字 PDF | 8 式：导数、三角积分、几何求和、极限、估计量、偏微分、复合根式等 | 8 / 8 |
| 保留集，扫描 PDF | 同 8 式 | 8 / 8 |

较早一轮同一模型的上述真实 HTTP 转换耗时分别约 72.6、72.1、90.2、93.7 秒，含初始化，使用已有模型缓存。最新干净 Python 环境复核中，单页初始文字样本为 75.442 秒、单页保留集扫描样本为 92.505 秒；另外两份单页教材为 273.389 和 246.226 秒，详见 `release-validation.json`。这些都是整份单页文件的完整请求耗时，包含初始化，不是固定每页速度；多页文档内部复用模型，不能直接乘页数。运行时有其他 CPU 任务，不能当作稳定性能基准，也不能按 PDF 的 MB 数推算其他文档耗时。

最新测试设备为 Intel Core Ultra 9 185H、约 32 GB 内存、Windows x64。当前依赖为 CPU 版 PaddlePaddle，worker 固定 CPU 4 线程；设备上的 RTX 4060 Laptop 未用于推理。首次依赖安装和约 900 MB 权重下载不包含在上述转换时间中，尚未实现 GPU 或模型常驻加速。

Java 集成增加了文字层中单字母变量大小写的保守校正；不会据标准答案修输出。原文字层本身映射错误时，这种校正也可能出错。旧 M 模型的早期低分辨率结果曾出现高斯分母和大小写错误，不计入上述结果。

## 真实教材复核与尚存问题

另外使用本地教材两页，实际 HTTP 检测分别得到 29 与 23 个区域。检测区域数包含误检，不等于真实公式总数；未预先完成全页逐式标注，因此不报告这两页的准确率百分比。教材及转换内容不纳入公开源码。

已修复并用相同真实模型响应重放核对的集成问题：

1. 公式一律以块插入导致行内阅读顺序中断。现在行内使用 `$...$`，独立公式使用 `$$...$$`。
2. 原图链接打断正文。文字页的公式原图链接移至该页正文后。
3. 多个公式编号被误判为双栏、部分编号落到公式后。采用占位字形参与排版并选择邻近正文/编号基线。
4. 大型积分符号的 PDF 锚点在检测框顶部，普通字形中心估计导致符号重复残留。调整区域判断后，两处重复积分符号已消除。
5. 模型输出 `align*` 嵌套于 Markdown 数学定界符。转为可嵌套的 `aligned`，保留公式内容。
6. 两个框把英文正文识别成数学命令。检测到常见英文正文词后，保留原文字层、原图及 `FORMULA_REVIEW_REQUIRED` 标记。

剩余问题明确阻止“公式高准确率验证已完成”的结论：

- 一处可预测过程定义中的带上下标表达式漏检，仍是原文字层的线性字符，未恢复成准确 LaTeX。
- 检测框混入正文的两个区域被保护后，没有自动完成该区域的公式转换。
- 检测不到的简单变量/上下标不会自动补全；常见英文词保护只是启发式，存在漏报和误报。
- 部分正文与行内公式边界缺空格；扫描页公式区域拼接与复杂多栏仍需人工核验。

相同模型响应的离线重放仅验证排版代码变化，不算新的模型推理，也不会扩大准确率样本数。最新版干净环境 HTTP 复核结果见同目录的 `release-validation.json`。

## 复现方法

从源码根目录运行：

```powershell
mvn package
# 合成样本生成器单独依赖，不属于工具运行所需依赖
py -m venv .venv-benchmarks
.\.venv-benchmarks\Scripts\python.exe -m pip install matplotlib==3.11.2 Pillow==12.3.0
.\.venv-benchmarks\Scripts\python.exe benchmarks/generate_formula_samples.py
```

按根 README 配置 OCR/公式模型并启动服务，再上传：

```powershell
py benchmarks/verify_formula_downloads.py benchmarks/data/math-layout.pdf
py benchmarks/verify_formula_downloads.py benchmarks/data/math-layout-scan.pdf
py benchmarks/verify_formula_downloads.py benchmarks/data/math-holdout.pdf
py benchmarks/verify_formula_downloads.py benchmarks/data/math-holdout-scan.pdf
```

脚本核验 JSON 与下载 `.md` 相同、ZIP 中 `.md` 相同、ZIP CRC 正常、每个检测区域有有效 PNG 原图。**不自动判定数学语义正确率**。应逐式对照生成目录的 reference JSON 和原 PDF。固定生成脚本使后续样本可重复，但字体库/版本及布局与本轮早期手动生成文件可能有差异；不能宣称字节相同或无需重测即可得到同一分数。

所有生成 PDF、结果 ZIP、模型、虚拟环境及用户数据均排除在源码包之外。
